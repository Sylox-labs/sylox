# ADR-009: asset_stale as a transition event

Status: Accepted, spec v1.2 · Date: October 8, 2026

## Context

`RiskOracle`'s first `asset_stale` design (spec v1.1, PR #2 Phase 2) fired when a newly observed epoch was itself already stale on arrival (a very late backfill). This never fires for the realistic failure mode: keepers simply stop posting. With no new epoch ever arriving, nothing triggers the check at all, so an asset can sit stale indefinitely with no event ever telling an integrator the feed died.

## Decision

`asset_stale` means the asset transitioned into stale, not that one newly observed epoch happened to be stale. `RiskOracle` tracks a per-asset `stale_announced` flag. A new permissionless read, `check_stale(asset) -> bool`, evaluates staleness against the epoch of the currently stored `RiskScore` (never the newest Final epoch the finality scan found, which can run ahead of the stored score when `recompute_score` declines to write, for example a sticky `Event` band or not enough history yet). If the asset is stale and `stale_announced` is not already set, it emits `asset_stale` once, sets the flag, and returns the current stale state; calling it again while still stale emits nothing.

The same check runs internally at the end of every state changing call that touches the asset (`post_signals`, `dispute_signals`, `resolve_signal_dispute`, `finalize_endpoint`), so a late backfill that is stale on arrival still gets announced without anyone needing to call `check_stale` explicitly, and the "keepers stopped posting" case is covered by whichever monitor or integrator calls `check_stale` directly, on a schedule, since no state changing call happens on its own while keepers are silent.

The flag clears the moment a fresh, non-stale epoch is scored; no separate recovery event is emitted, since `score_updated` already signals that a fresh score landed. A later relapse into stale emits `asset_stale` again, exactly once, the same way the first transition did.

A monitoring job calls `check_stale` for every registered asset once per epoch (Section 22.4), which is what makes the "keepers stopped posting" case actually surface an event in practice, independent of any asset-specific state changing call ever happening again.

## Consequences

- `asset_stale` reliably fires for every way an asset can go stale: keepers stopping entirely, and a late backfill that is stale on arrival.
- `score().stale` and `is_stale()` remain two different signals (ADR-005, Section 5.5, 5.7): `is_stale()` judges against the newest posted epoch, `score().stale` and `check_stale` both judge against the stored score's own epoch. An integrator that only reads `is_stale()` can still see `false` while the asset has been stale, and announced as such, for some time; `check_stale`'s own return value and the `asset_stale` event are the authoritative signal for "has this asset gone stale," not `is_stale()`.
- `check_stale` is permissionless and read-mostly (it writes only the one flag, never a score), so any integrator or monitor can call it freely; it carries no incentive or rate limiting design, since nothing about it needs one.
- New API `check_stale`; new storage `StaleAnnounced(asset)`.

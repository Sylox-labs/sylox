# ADR-011: Removal is never an escape hatch

Status: Accepted, feat/staking · Date: October 9, 2026

## Context

`Staking` lets governance remove a keeper or reporter (`remove_keeper`, `remove_reporter`) and lets either voluntarily exit their own stake (`unstake_request`/`unstake`). Neither path is in Section 7.7's state diagram as written: v1.1/v1.2 described `Suspended -> [*]: remove_reporter` and a voluntary `Unstaking` cooldown as if they released funds immediately or near-immediately. Built against the real failure modes this exposes three separate ways removal or a voluntary exit could be used to dodge consequences that a few more minutes, hours or days of normal operation would otherwise still catch:

1. A reporter submits probes that disagree with a 3+ majority, is removed before `settle_probes` ever runs for that epoch, and its stake leaves before the fault and slash land.
2. A keeper's posting is disputed; the keeper is removed before the dispute resolves, and its bond is withdrawn while the dispute (and the slash it might produce) is still open.
3. A reporter's own voluntary `unstake_request` exits faster than a governor-initiated removal would have allowed for the exact same underlying stake, making removal itself pointless as a deterrent.

## Decision

Removal deactivates a keeper or reporter **immediately** (no new postings, no new probes: `is_active_keeper` reads `false`, `submit_probe` rejects with `Suspended`), but never releases funds on that same call. Funds leave only through a separate, later step, gated by one of two independent conditions, both of which must hold:

- **An exit delay from removal**, long enough that every epoch or posting the removed party could have been held accountable for has had its full window to run:
  - `KEEPER_EXIT_DELAY_SECS = SIGNAL_DISPUTE_SECS + EPOCH_SECS`: a keeper's most recent posting can be up to one epoch before removal (posted right before the epoch closed), and its own dispute window is `SIGNAL_DISPUTE_SECS` from that post.
  - `REPORTER_EXIT_DELAY_SECS = EPOCH_SECS + PROBE_GRACE_SECS + SETTLE_WINDOW_SECS`: a reporter's most recent probe can be for an epoch up to one `EPOCH_SECS` before removal, and that epoch's own settlement window runs `PROBE_GRACE_SECS + SETTLE_WINDOW_SECS` past its close.
  - Both are `const` expressions of the parameters they are built from, not separately hardcoded numbers, each proven to cover the claimed span by a dedicated test (`params::params_test`), not just asserted in a comment.
- **No open accountability action naming that party.** For a keeper, `open_dispute_count == 0`: every `BondKey::SignalDispute` bond naming this keeper as `subject` has been released or forfeited. A removed keeper can still be slashed by a dispute resolution (or, per ADR-010, a ruling timeout) that arrives before withdrawal; the bond's own settlement, not the exit delay's elapsed time alone, is what finally allows `withdraw_keeper_bond` to pay out.

Stake in cooldown stays fully slashable until the moment it is actually paid out. `unstake`/`settle_probes`/`slash` all operate on the same stored balance regardless of whether an `unstake_request` is pending; cooldown is a timer on withdrawal, not a freeze on liability.

Voluntary exit is capped at the same floor: `UNSTAKE_COOLDOWN_SECS >= REPORTER_EXIT_DELAY_SECS` and `>= KEEPER_EXIT_DELAY_SECS`, asserted by `params_test::voluntary_unstake_cooldown_is_at_least_the_removal_exit_delay`. A party cannot use its own voluntary `unstake_request` to exit faster than a governor removal would have allowed for the identical stake; the cooldown duration is a decision about how long the funds genuinely stay at risk, not a convenience knob the party being removed could outrun by acting first.

A reporter's probe is evaluated for aggregation and settlement using the region it registered with **at the time it submitted that probe** (`StoredProbe.region_at_submission`), read from a snapshot taken at `submit_probe` time, never a live lookup of the reporter's current registration. This is what makes "removal is not an escape hatch" hold even for data, not just funds: a reporter removed after submitting a probe does not retroactively change what region that probe counted toward, and `aggregate`/`settle_probes` for an epoch produce the same result whether or not a contributing reporter was later removed.

## Consequences

- `withdraw_keeper_bond` (removal path) and `unstake` (voluntary path, for a keeper) both check `open_dispute_count == 0` independently, since a voluntary exit while still registered is a real code path distinct from governor removal and needs the identical guard.
- A removed party's bond or stake can sit locked for `KEEPER_EXIT_DELAY_SECS`/`REPORTER_EXIT_DELAY_SECS` even with no open dispute, by construction (the delay and the dispute check are both required, not alternatives); this is accepted as the cost of the accountability window, not treated as a bug to shorten.
- The submitter index (`Submitters(asset, epoch)`) and the region snapshot together mean `aggregate`/`settle_probes` never consult the live reporter or keeper registry for already-submitted data; only `submit_probe`/`post_signals` themselves (new activity) check current registration and active status.
- New parameters `keeper_exit_delay_secs` (derived, 3h at defaults) and `reporter_exit_delay_secs` (derived, 26h at defaults), both derived expressions, not independently configurable; see Section 23.
- Sections touched: technical-doc.md 7.3, 7.7, 12.3, 15.1, 23.

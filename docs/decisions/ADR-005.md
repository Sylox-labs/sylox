# ADR-005: Oracle robustness

Status: Accepted, spec v1.1 · Date: October 8, 2026

## Context

Several v1.0 oracle rules made outcomes fragile:

- Keepers could post only the current or previous epoch, so a short keeper outage, or an overturned posting, left permanent gaps.
- Missing epochs counted as failing a Depeg check, so gaps could help trigger an event.
- The Depeg liquidity floor compared each epoch's live liquidity with `min_liquidity`, so a real run on an issuer, which drains liquidity, could block the payout it should trigger.
- `peg_ratio_min`, the lowest value in the window, let one wick at a bad price force a band change.
- The keeper posted the endpoint status, although it is the reporters' signal.
- `supply` was said to be cross checked against the SAC, but SEP-41 has no `total_supply`.
- Tier 1 checks implied reading 72 separate `Signals` entries.
- The reporter aggregation rule mentioned "the most severe status reported by a strict majority", which mixes two rules.

## Decision

- **Backfill:** keepers may post any closed epoch inside the current `window_secs` that is not yet Final. An overturned epoch reopens for reposting instead of becoming a gap.
- **Missing epochs:** add `max_missing_epochs` (default 6 of 72) to the Depeg definition. Missing epochs count neither for nor against; Depeg triggers if every present epoch fails and missing epochs are at most `max_missing_epochs`.
- **Disputes** do not reset the window; a disputed epoch stays non final and is reposted if overturned.
- **Liquidity floor:** compare `min_liquidity` with the median liquidity of the 7 days before the window started. A live liquidity collapse is its own signal (component L and a committee input), never a reason to block a payout.
- **`peg_ratio_p10`** (10th percentile of the volume weighted price series in the window) replaces `peg_ratio_min`.
- **Endpoint status** comes only from the `Staking` aggregate. The `endpoint` field stays on `SignalSet`, but `RiskOracle` overwrites it and ignores any keeper value; keepers post `Unknown`. `finalize_endpoint` lives on `RiskOracle` and reads `Staking.aggregate`.
- **Supply** is keeper posted from ledger asset stats, verified by recomputation only.
- **Ring buffer:** Tier 1 checks read one ring buffer entry per asset, with a finality flag per epoch slot, never separate `Signals` entries. Its write cost must be benchmarked in the first week of the `RiskOracle` build, with a fallback of paging it into entries of 24 slots.
- **Reporter aggregation:** status = the status reported by a strict majority; if there is no strict majority, Degraded.

## Consequences

- Keeper outages shorter than the window leave no gaps; longer ones leave missing epochs that the Depeg check tolerates up to a limit.
- A real depeg with a liquidity collapse can trigger; a market that was already empty before the window still cannot.
- Bands move on sustained prices, not single trades. The old sanity bound `peg_ratio_min <= peg_ratio` is dropped: a 10th percentile can sit above a volume weighted mean.
- Keepers cannot influence the endpoint signal at all.
- The ring grows to 240 slots (10 days: a 72 hour window plus the 7 day baseline), about 29 KB packed, which makes its write cost the main open performance question.
- Keeping the `endpoint` field on `SignalSet` (rather than removing it) avoids a wider type change; the cost is a field whose keeper supplied value is meaningless, documented as such in the type and the spec.

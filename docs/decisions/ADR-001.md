# ADR-001: Canonical event definitions

Status: Accepted, spec v1.1 · Date: October 8, 2026

## Context

In v1.0 a series referenced one `EventDefinition` by hash, and a definition listed several event kinds. Nothing stopped two series on the same asset from using different definitions, so one failure could be judged by different rules for different buyers, and a proposer could pick whichever definition was easiest to trigger. Event status was kept per asset, so a declared event of one kind (for example WithdrawalHalt) blocked any later event of another kind (for example Depeg) on the same asset.

## Decision

- There is one canonical, versioned `EventDefinition` per (asset, kind), registered by governance. Registering a new one creates the next version; old versions are never edited.
- Events are keyed by (asset, kind, def_version). `event_status` is per (asset, kind), so a Declared WithdrawalHalt never blocks a later Depeg.
- `SeriesTerms` pins one def_version per covered kind, as `def_versions: Map<EventKind, u32>`, replacing `event_def_hash`.
- `propose_tier1` takes (asset, kind) and always uses the current canonical version. Tier 2 and Tier 3 proposals do the same.
- After any Declared event on an asset, `MarketFactory` blocks new series on that asset until governance re-enables it. Re-enabling means registering a new canonical version for every Declared kind on the asset (possibly with identical parameters).
- A new version for (asset, kind) can be registered only when no live series pins the current version for that kind (`DefinitionInUse`), and `open_series` accepts only current versions. Together these keep invariant I13: every live series pins the canonical version of each kind it covers.

## Consequences

- Every buyer of cover on an asset is judged by the same rules for a given kind, and proposers cannot shop for a definition.
- Event kinds are independent: a failure of one kind does not hide a later failure of another.
- Because live series always pin the current version, `event_status(asset, kind)` is unambiguous for every series that reads it.
- Changing a definition is deliberately slow: governance must let series pinned to the old version run off (at most one term plus its post expiry period) before the new version can be registered.
- `EventRegistry` reads `MarketFactory.series_for(asset)` and each series' terms during registration (at most `max_series_per_asset` reads), so it needs the factory address at `initialize`.

# ADR-008: Per-epoch independent finality

Status: Accepted, spec v1.2 · Date: October 8, 2026

## Context

ADR-005 added backfill and the per-slot finality flag, but `RiskOracle`'s first implementation (PR #2, Phase 2) tracked the newest Final epoch with a sequential cursor: a stored pointer that advanced one epoch at a time, starting from wherever it last stopped, and stopping again at the first epoch found not yet Final. A permanently missing epoch (an outage longer than `window_secs`), an overturned epoch that was never reposted, or a dispute the committee never ruled on therefore blocked every later epoch's finality and the score behind it, indefinitely, even though every one of those later epochs had individually closed and become Final long before. Because staleness was judged against the newest *posted* epoch, a score frozen this way could also read as fresh.

## Decision

Finality is per epoch and fully independent: no epoch's state affects whether a later epoch can become Final. The newest Final epoch is found by scanning backward from the newest posted epoch, across the full backfill window (`window_secs / epoch_secs + 1` epochs, 73 at the defaults, never more than the ring's own 240 slots), skipping any epoch found missing, Disputed, or still Pending without stopping the scan. This scan runs on every state changing call that touches the asset (`post_signals`, `dispute_signals`, `resolve_signal_dispute`, `finalize_endpoint`).

The score is always computed from the newest Final epoch the scan finds. Inside that epoch's aggregate windows, a missing epoch (`Empty`, Disputed, or still Pending at scan time) is excluded from the sum or percentile it would have contributed to, never counted as zero and never blocking the aggregate: the 24 hour and 7 day sums (`redemption_net_24h`, `clawback_amount_7d`, `auth_revocations_7d`) skip it; `peg_ratio_p10`'s percentile input excludes it, failing closed only if every epoch in the Depeg window is missing. The hysteresis down streak still advances at most once per genuinely newer scored epoch: `recompute_score` only recomputes and persists a new `RiskScore` when the scan's newest Final epoch is strictly newer than the stored score's own epoch, no matter how many individual epochs a single scan discovers and announces.

`signals_final` is emitted per epoch the first time it is observed Final, tracked by a one byte `final_announced` flag added to each ring slot (the packed layout's previously unused padding byte; layout version bumped to 2). Because the scan can discover several epochs Final in one call, and a backfilled epoch can become Final later than a newer epoch that was posted on time, `signals_final` events can arrive out of epoch order.

`resolve_signal_dispute`'s `keeper_wins` path sets the resolved epoch Final and emits its `signals_final` directly, in the same call, rather than waiting for the scan to notice it; the scan still runs afterward for any other epoch the resolution may have unblocked.

## Consequences

- A keeper outage longer than the backfill window, an epoch nobody ever reposts after an overturn, or a dispute the committee never rules on no longer blocks any other epoch: the score keeps advancing to the newest epoch that did become Final, and the frozen epochs are simply excluded from its aggregates as missing data.
- A score computed from a genuinely old epoch still reads stale, judged against that epoch, independent of whether anything newer has been posted; staleness is not masked by unrelated posting activity on the same asset (ADR-009 makes this precise for the `asset_stale` event specifically).
- `signals_final` is not safe to assume monotonic by epoch; an indexer must order by ledger and dedupe on `(asset, epoch)`, not assume epoch order (Section 13.1).
- The scan's cost is bounded (at most 73 epochs per call) and stays small in practice: a measured worst case (a full 240 slot ring plus a 71 epoch missing gap) cost 2.39M CPU instructions, 0.60% of `tx_max_instructions`.
- Ring buffer layout version 2: byte 106 of each packed slot (previously unused padding) holds `final_announced`. No migration path is defined, since no contract using layout version 1 has ever been deployed.

# Sylox App

The app people use to see an issuer's risk, provide cover, buy cover, and claim. Talks to the Soroban contracts directly, through generated TypeScript bindings. No backend.

## Running it

From the repo root (this is an npm workspace member, not a standalone project):

```bash
npm install
npm run dev -w web/app
```

## Contract bindings

`lib/contracts/<name>/` is generated by `stellar contract bindings typescript`, one directory per contract, against the contract IDs in `deployments/testnet.json`. Never hand-edit the generated `src/index.ts` files; regenerate instead:

```bash
npm run bindings:generate -w web/app
```

This requires `stellar` CLI **28.1.0** exactly (the version `deploy/deploy.sh` pins) and fails loudly if a different version is installed, rather than silently generating bindings that might not match the deployed contracts' actual ABI.

`lib/contracts/deployment.ts` is the one place in the app that reads `deployments/testnet.json`; every contract client is built from it. No contract address is ever written as a literal in app code, so a testnet redeploy (new contract IDs) is a non-event for the app.

The generated bindings are committed (not gitignored): CI has no network path to regenerate them against live testnet, so it builds against the committed copy like any other source file.

## Screens

- **Explorer** (`/`): every tracked asset, its current risk band, score, staleness, and event status, read live from RiskOracle. Done.
- **Asset** (`/asset/[id]`): header, Confirmed/Live peg price, peg history chart, failure definitions, cover-sale status, active-event indicator (links to each event the asset currently has in progress). Done.
- **Event** (`/event/[id]`): proposal details, a countdown to the real challenge/ruling deadline, Depeg cure progress, and the Checkpoint/Finalize write actions. The first screen that writes to the contracts - see "Wallet" below.
- **Events** (`/events`): every proposed event read from EventRegistry, newest first, each linking to its Event screen - see "RPC getEvents pagination" below for how this actually finds them.
- Markets, Faucet: not built yet.

## Navigation

Every screen is wrapped in `components/DashboardShell.tsx`: a persistent sidebar (Explorer, Events, plus "Soon"-tagged placeholders for Markets/My positions/Faucet, and an External section linking the website, docs, and this repo) and a top bar (page title, a fixed Testnet badge, Connect Wallet). On narrow widths the sidebar collapses into a menu button that opens a drawer, with the same focus-trap/Escape handling as `WalletPickerModal`. Explorer, Asset, Event, and Events all stay fully readable with no wallet connected - the shell never gates them behind a "Connect your wallet" screen; only an actual write action (Checkpoint, Finalize) prompts for a connection when clicked, same as before the shell existed. A future screen showing the visitor's own data (My positions) is the first candidate for an actual wallet-gated empty state, once it's built.

## Wallet

The Event screen is the first to write to the contracts, so it's the first to need a connected wallet. Stellar Wallets Kit (`lib/wallet/kit.ts`) provides the actual wallet connections (Freighter, xBull, Albedo - each imported by its own subpath, not `defaultModules()`, which pulls in every "no extra config" module the kit ships), used strictly for its headless SDK - the kit's own built-in modal is never shown. The picker UI itself (`@sylox/ui`'s `WalletPickerModal`) is the shared design system's own component, driven by plain props; `web/shared/ui` never imports the kit.

The kit is loaded with a dynamic `import()` only when the picker actually opens (`lib/wallet/kit.ts`), not on every page load, so its bundle never ships to a visitor who never connects a wallet.

**SDK version boundary (temporary, see issue #37):** the kit bundles its own `@stellar/stellar-sdk` (17.x), while this app is pinned to 16.x (what the generated contract bindings were built against). Only plain XDR strings cross between the kit and the app's own write-action code (`lib/event-actions.ts`) - never a `Transaction` or other SDK object, since those can fail type checks across versions even when TypeScript compiles cleanly. Issue #37 tracks upgrading `web/app` to 17.x and regenerating the bindings, which removes this boundary rule entirely.

**Dev-only fixtures:** `/event/fixture-proposed`, `-challenged`, `-cured`, `-declared` render from typed mock data (`lib/event-fixtures.ts`) instead of the live contract, so the screen's layout/countdown/buttons can be checked without a real event on testnet. Loaded only through a dynamic `import()` gated on `process.env.NODE_ENV !== "production"`, so the whole module - and every string in it - is stripped out of a production build, not just hidden behind a runtime check (verified by grepping the production bundle). A fixture id in a production build falls through to the live fetch and 404s on it like any other invalid id; a real numeric `event_id` always uses the live contract read, in every environment.

## RPC getEvents pagination

`lib/stellar-rpc-events.ts` is the one place this app scans the RPC's event log (used by the Events screen and could be reused for any future activity feed, e.g. `signals_posted`). Its design is the direct result of testing `getEvents` against our own deployed contracts on `soroban-testnet.stellar.org`, since several things about its real behavior aren't documented anywhere:

- **`endLedger` is exclusive**, confirmed empirically: a query with `endLedger` set to a real event's own ledger excluded that event; `endLedger` set to `ledger + 1` included it. Every range this file builds is half-open, `[start, end)`.
- **A single `getEvents` call only ever advances its cursor by roughly 10,000 ledgers** (`CHUNK_SIZE` in `stellar-rpc-events.ts`, with a comment dating the measurement), regardless of how wide a range is requested, `endLedger`-bounded or not. It does not error when it stops short of the requested range - it just returns whatever it found in the portion it actually scanned (zero, for a quiet slice) together with a cursor pointing just past where it stopped. Measured directly at 2,000/16,000/32,000/64,000-ledger requests: each advanced by about the same ~10,000 ledgers, meaning a wider requested range buys nothing - a 64,000-ledger request still took 7 cursor-followed calls to fully cover. This ruled out an earlier design that tried growing the chunk size for a sparse topic; it bought nothing, since the real limit is per-request, not per-requested-range.
- **This means a single wide, unchunked `getEvents` call across the RPC's full claimed retention window (`getHealth()`'s `oldestLedger`, ~7 days) can silently return zero results past about 19,000-19,200 ledgers back (~27 hours)** even when real matching events exist further back, if nothing matched in the ~10,000-ledger slice it actually scanned before stopping. An empty response is never proof an empty range - it only proves the portion actually scanned (which the response's own cursor reveals) was empty.
- **The fix is backward chunking, newest-first:** since `getEvents` only pages forward (oldest cursor → newest), and this app needs newest-first results, `lib/chunk-plan.ts`'s `planChunks()` (a pure, independently-tested function - see its own test file for the boundary cases: exact multiples, remainders, single-chunk windows, `latest == floor`, and a real-world 61-range window) plans whole `CHUNK_SIZE`-ledger ranges walking backward from `latestLedger`. `lib/stellar-rpc-events.ts` fetches each range in turn (normally one request per range, cursor-following only if a range itself needs more than one call), stopping once enough events are found or the floor is reached.
- **The retention floor itself moves forward continuously** (about one ledger every 5-6 seconds) while a multi-chunk scan runs, so a single `getHealth()` snapshot taken at the top of the scan can go stale by the time a later chunk's request fires - reproduced directly. Real drift during a scan is only a handful of ledgers, and only the very last chunk (nearest the floor) is ever at risk, so rather than re-fetching `getHealth()` on every chunk (or parsing the exact wording of the RPC's error message, which isn't a stable contract), the scan just stays clear of the floor with a small margin (`FLOOR_MARGIN`, ~8-10 minutes of ledgers) and keeps one bounded retry (re-fetch health, re-clamp, try once more) as a safety net if a request still lands out of range despite the margin. `REQUEST_CAP` is the hard backstop regardless - the scan always stops and returns whatever it already has rather than retrying indefinitely.
- **Chunk growth was tried and reverted.** An earlier version doubled the chunk size (2k→4k→8k…) for a sparse topic, on the assumption that a wider requested range costs about the same as a narrow one. Measured directly, that's false (see the per-request limit above) - growth bought nothing, so `CHUNK_SIZE` is fixed at the RPC's own real per-request scan distance instead.

**Caching is the actual efficiency win, not chunk size.** Events in already-scanned ledgers never change, so `fetchEventsPaginated()` keeps a cache per `(network, contract, topics)` and, on a refresh, only scans forward from the newest ledger already covered - normally 1 request - instead of repeating the whole backward walk. The cache mirrors into `sessionStorage` (this app has no backend - the top of this file - so there is nowhere shared to put it; each browser tab warms its own) so a page reload doesn't pay a cold scan again either, and every read/write is wrapped in `try`/`catch`, falling back to memory-only if storage is unavailable. A stale cached event whose ledger has since aged below the moving floor is dropped on the next read, whether that read is a fresh scan or just a warm, already-covered check.

**Measured, live against testnet, after this design:**

| Scenario | Cold (first load) | Warm (cache hit/refresh) |
| --- | --- | --- |
| Busy topic (`signals_posted`, 25 real events ~13h back) | 5 requests, ~1.8s | 2 requests, ~0.5s |
| Empty topic (`event_proposed`, 0 real events exist yet) | ~14 requests, ~3.7-5.9s (full ~7-day window, never hits `REQUEST_CAP`) | 2 requests, ~0.5s |

The Events screen's "Events in the last N days" label is worked out from the ledger range a scan actually covered (`oldestLedgerScanned`), never a fixed 7 - a scan that stops at `REQUEST_CAP` before reaching the floor says so explicitly ("No events found in the last N days scanned"), rather than reading as if the full claimed window was checked when it wasn't.

**Stopgap, not the long-term design.** `EventRegistry` doesn't yet expose a direct read listing every event it has ever stored - `lib/events-list-data.ts`'s `listRegistryEvents()` scans the `event_proposed` log entry for each event's id, then reads its *current* state with `event(event_id)` (the log entry itself is frozen at proposal time). Once a direct enumeration read exists on the contract, swapping it in is meant to be a one-function change inside `listRegistryEvents()`, not a rewrite of the Events screen. The `getEvents` scan itself stays the right mechanism for a genuine activity feed (e.g. `signals_posted`), which has no other direct read.

## Deployment

Served from Railway as its own service, separate from the `web/landing` service - `web/app` needs a live `next start` process (dynamic server-streamed content on `/asset/[id]`), not a static export.

Built from `web/app/Dockerfile`, not Railpack. Railpack's own build-plan resolution in this monorepo consistently ran `web/landing`'s `package.json` scripts regardless of this service's dashboard-configured custom build/start commands - reproduced across three separate Railway services/projects, with the repo-root `railpack.json` (needed so Railpack detects Node rather than Rust at the repo root - see its own commit history) logged as the authoritative config source each time, overriding the dashboard's build command specifically. A Dockerfile has no auto-detection step to get wrong: `docker build -f web/app/Dockerfile .` from the repo root runs exactly `npm install`, `npm run build -w web/app`, then (on container start) `next start -w web/app -- -p 3000` - nothing else. The service's build/start commands and root directory are set directly in the Railway dashboard, not config-as-code, which never took effect for a service created after Railway's 2026-08-28 deprecation cutoff (a `web/app/railway.json` from that earlier attempt has since been deleted).

**Port.** The container always listens on 3000 (`EXPOSE 3000` + a hardcoded `-p 3000` in the Dockerfile's `CMD`, not Railway's `$PORT`) - an earlier attempt that read `$PORT` as a literal shell variable crash-looped, because the dashboard's leftover custom Start Command was overriding the Dockerfile's `CMD` without going through a shell that would expand it. Railway routes to the container by the custom domain's own **target port**, set to `3000` when `app.sylox.xyz` was attached (`railway domain app.sylox.xyz --port 3000`), not via a `PORT` environment variable - the service has no `PORT` variable set at all. If the Dockerfile's listen port ever changes, the domain's target port (Settings → Networking → the domain's own port field) has to change with it, or the site silently stops routing.

The build needs the whole monorepo (repo root, not `web/app/` alone) in its Docker build context, since `web/app` depends on the `web/shared/ui` workspace member for npm's workspace resolution to find it.

**Environment variables:** just `NODE_ENV=production`, set explicitly on the service - no `PORT` variable (see "Port" above: routing uses the domain's own target port, not `$PORT`). The app has no server-side secrets, API keys, or other runtime config - every contract address it reads comes from the committed `deployments/testnet.json`, and all RPC calls go straight from the browser to the public Soroban RPC endpoint (see "No backend" above).

**Deploys via GitHub Actions, not Railway's own auto-deploy.** Railway's watch-path evaluation has been observed skipping deploys that genuinely touched a watched path - confirmed on a real push to `main` (a merge that changed `web/app/components/WalletButton.tsx`, squarely inside the then-watched `/web/app/**` pattern, logged `skippedReason: "No changes to watched files"`) - and, separately, skipping *every* direct `railway up` upload outright regardless of what changed: an upload carries no changed-files list for Railway to diff against, so with any watch paths set at all it always concludes nothing matched. Reported to Railway support.

**`sylox-app`'s Railway watch paths must stay empty.** That's the actual fix on our side, independent of whatever Railway's own investigation finds - with them cleared, Railway never runs its own (buggy) skip check against this service, full stop. Don't re-add them. `.github/workflows/ci.yml`'s `deploy-sylox-app` job does the path filtering instead: it runs after every other CI job passes on a push to `main`, diffs the whole push (`github.event.before..github.sha`, not just the latest commit) against `web/app/**`, `web/shared/**`, `deployments/**`, `package.json`, `package-lock.json`, and only then deploys with a pinned Railway CLI version (`npm install -g @railway/cli@5.64.2` - the same version this workflow was built and tested against; bump deliberately, not via `@latest`). `sylox-app`'s own Railway auto-deploy is turned off once this workflow has deployed successfully at least once. `web/landing` is unaffected: it keeps its own watch paths and its existing Railway auto-deploy, which has been reliable.

## Rules this app follows

- **Contract reads only, never recomputed.** Staleness, band, and score all come from the contract's own `check_stale`/`band`/`score` calls. The app never re-derives these from raw epoch/timestamp math, because the contract's actual staleness threshold isn't even exposed as a public read (see `lib/explorer-data.ts`'s doc comments).
- **Testnet labeled everywhere.** `components/TestnetBanner.tsx` renders on every page.
- **No marketing claims.** No "insured," no "guaranteed returns," no APY, the word "insurance" never appears.
- **Every write is simulated before it's signed.** A contract method that changes state is always constructed (which auto-simulates) first; its result is shown in plain words before the wallet is ever asked to sign anything (`lib/event-actions.ts`'s `prepare*`/`confirm*` split).
